## 1. Run lifecycle (`run_agent()` in `runtime/runs/worker.py`)

`run_agent(bridge, run_manager, record, *, ctx: RunContext, agent_factory, graph_input, config, stream_modes, stream_subgraphs, interrupt_before, interrupt_after)` executes one run inside an asyncio task, publishing to a `StreamBridge` [Verified from source: runtime/runs/worker.py:496-510]. `RunContext` groups `checkpointer, store, event_store, run_events_config, thread_store, app_config, checkpoint_channel_mode ("full" default), checkpoint_snapshot_frequency, on_run_completed` [Verified from source: runtime/runs/worker.py:376-395].

Numbered sequence:

1. **Admission (before the worker)** — `RunManager.create_or_reject()` → `_admit_thread_operation()` admits the run under the manager lock: local inflight check, durable insert via `RunStore.create_thread_operation_atomic()` (cross-worker uniqueness = partial unique index `uq_runs_thread_active` on `thread_id WHERE status IN ('pending','running')`), then local registration; `multitask_strategy` must be one of `("reject", "interrupt", "rollback")` [Verified from source: runtime/runs/manager.py:1376-1639, 1476-1478; persistence/run/model.py:60-74]. Unique violations surface as `ConflictError` [Verified from source: runtime/runs/manager.py:1545-1588].
2. **Stream mode normalization** — `normalize_stream_modes()` accepts only `values, messages-tuple, updates, debug, tasks, checkpoints, custom` (default `["values"]`), raising `UnsupportedStreamModeError` otherwise; `to_langgraph_stream_modes()` maps `messages-tuple` → LangGraph `messages`, nothing else [Verified from source: runtime/stream_modes.py:7-47; worker.py:599-601]. `events` mode is rejected because it requires `astream_events()` which cannot co-produce `values` snapshots [Verified from source: worker.py:10-13].
3. **Journal construction before preflight** — when an `event_store` exists, `RunJournal` is built *before* any fallible/cancellable preflight so every terminal run can emit a `run.delivery` receipt; a separate flag `persist_completion` (set True only after preflight succeeds, line 671) preserves the old boundary so early failures do not write an empty completion snapshot [Verified from source: worker.py:543-547, 602-616, 671].
4. **Wait for prior finalizing + start barrier** — `run_manager.wait_for_prior_finalizing(thread_id, run_id, abort_event=...)` polls until older same-thread runs finish post-cancel cleanup; then `try_start(run_id)` does the durable pending→running CAS (`RunStore.start_run`); a non-`started` outcome ends the run (with `_finish_cancellation(record.abort_action, restore_checkpoint=False)` if aborted) [Verified from source: worker.py:618-632; manager.py:771-818, 1018-1048]. Thread meta status is set to `"running"` only after start succeeds [Verified from source: worker.py:634-638].
5. **Checkpoint-mode preflight (compatibility gate)** — `inject_checkpoint_mode(config, mode)` stamps `configurable.__deerflow_checkpoint_channel_mode` and (delta only) `metadata.deerflow_checkpoint_channel_mode="delta"`; `aensure_checkpoint_mode_compatible` is run against the head config and, if the caller selected `checkpoint_id`/`checkpoint_map`, against that selector too [Verified from source: worker.py:639-669; runtime/checkpoint_mode.py:81-88, 138-143].
6. **Pre-run workspace snapshot** — `capture_workspace_snapshot(thread_id, user_id)` is captured (best-effort) when an event store exists; used later for the workspace-changes event and the delivery verdict [Verified from source: worker.py:673-681].
7. **Metadata publish** — `bridge.publish(run_id, "metadata", {"run_id", "thread_id"})` (needed by `useStream`) [Verified from source: worker.py:683-691].
8. **Runtime context + callbacks** — `_build_runtime_context()` always includes `thread_id`/`run_id` (caller `config["context"]` merged with `setdefault`, never overriding those), plus `app_config`; the journal is exposed as `runtime_ctx["__run_journal"]` and appended to `config["callbacks"]`; Langfuse trace metadata is injected; `run_name` resolves via `resolve_root_run_name()` (context/configurable `agent_name`, else `assistant_id`, else `"lead_agent"`) [Verified from source: worker.py:347-373, 701-741; runtime/runs/naming.py:9-16].
9. **Agent build + accessor bind** — `agent_factory(config=..., app_config=...)`; `CheckpointStateAccessor.bind(agent, checkpointer, store=store, mode=mode)` [Verified from source: worker.py:753-763].
10. **Rollback point capture (under `_checkpoint_thread_lock(thread_id)`)** — `_capture_rollback_point()` materializes pre-run state through the accessor and captures raw `pending_writes` into an immutable `RollbackPoint(config, state_values, messages, metadata, pending_writes)`; any capture failure sets `snapshot_capture_failed` and disables rollback (fail-closed); `pre_existing_message_ids` is collected from the captured messages to mask stale `deerflow_error_fallback` markers from prior runs [Verified from source: worker.py:765-786, 528-532; 1551-1599].
11. **Delta resume linearization (same lock)** — `_linearize_delta_checkpoint_resume()` rewrites a delta-mode resume-from-older-checkpoint as a linear head write (see §2); when it fires, `pre_existing_message_ids` is recomputed from the resumed state and `initial_runnable_config` rebuilt (the `checkpoint_id`/`checkpoint_map` selectors were popped) [Verified from source: worker.py:788-807, 1632-1718]. The pre-existing id set is then exposed in runtime context under `__deerflow_pre_run_message_ids` [Verified from source: worker.py:806-807; runtime/context_keys.py:5].
12. **Effective model name** — if the agent's `metadata["model_name"]` differs from the requested one (allowlist fallback), `run_manager.update_model_name()` persists the actual model [Verified from source: worker.py:809-818].
13. **Attach checkpointer/store, interrupt nodes** — `agent.checkpointer = checkpointer`, `agent.store = store`, `agent.interrupt_before_nodes` / `interrupt_after_nodes` set when provided [Verified from source: worker.py:820-830].
14. **Graph streaming loop (`_stream_once`)** — held under `_checkpoint_thread_lock(thread_id)`. Single mode + no subgraphs: `agent.astream(input, stream_mode=single_mode)` yields raw chunks; multi-mode/subgraphs: yields tuples unpacked by `_unpack_stream_item()` into `(mode, chunk, namespace)`. Every iteration checks `record.abort_event.is_set()` and breaks on abort. Root-namespace frames only feed `_extract_llm_error_fallback_message()` (subagent fallbacks are the executor's to map). Publishing goes through `_publish_stream_item()`: namespaced frames publish under `mode|ns1|ns2` (LangGraph Platform style) and bypass root-only consumers; root `messages` frames pass through `_LargeFileToolChunkBatcher` (only when `values` is also requested) which batches `str_replace`/`write_file` argument deltas in batches of `_LARGE_FILE_TOOL_BATCH_SIZE = 32`; `custom` chunks are also fed to the `_SubagentEventBuffer` [Verified from source: worker.py:850-906, 2215-2292, 226-344, 852]. SSE event names map 1:1 from LangGraph mode names (`"messages"` stays `"messages"`) [Verified from source: worker.py:2084-2093].
15. **Goal continuation loop** — after the visible turn, while not aborted and no LLM error fallback: `_prepare_goal_continuation_input()` evaluates the active goal (see §5) and, if it returns a hidden continuation input, streams another turn with `_continuation_runnable_config()` (copy of config with `checkpoint_ns=""` and `checkpoint_id`/`checkpoint_map` removed). Stale `stop_reason` is cleared only before the first user-visible turn — a cap hit during the user turn survives clean hidden turns [Verified from source: worker.py:908-932, 744-751].
16. **Terminal status staging** — three branches: (a) aborted → `_finish_cancellation(record.abort_action)`; (b) LLM error fallback (streamed marker or `journal.had_llm_error_fallback`) → `set_status_if_not_cancelled(error, error_msg)` with default message `"LLM provider failed after retries"`; (c) success path → read `stop_reason` from runtime context (values: `loop_capped`, `token_capped`, `safety_capped`, `subagent_limit_capped`, `model_length_capped`), compute `produced_output_paths` (workspace diff), build `delivery_content`, and set `error` status with `_DELIVERY_INCOMPLETE_ERROR = "Artifact delivery incomplete: no produced output artifact was presented"` when produced outputs were not covered by a `present_files` path, else `success` [Verified from source: worker.py:934-986, 163-165, 176-205, 951-967]. When `event_store` is configured, all terminal `set_status` calls in the try-body pass `persist=False` — status is *staged* in memory and durably persisted only after the delivery receipt (see step 19) [Verified from source: worker.py:518, 1061-1065].
17. **Cancellation finisher** — `_finish_cancellation(action)`: sets `finalizing=True`; `action == "rollback"` → status `error` with `"Rolled back by user"` and `_rollback_to_pre_run_checkpoint()`; otherwise status `interrupted` [Verified from source: worker.py:554-596]. `asyncio.CancelledError` and generic exceptions route through the same finisher / `set_status_if_not_cancelled` + `bridge.publish(run_id, "error", {message, name})` [Verified from source: worker.py:988-1011].
18. **Finally: ownership fence + edit-replay rollback** — a fenced worker (`record.ownership_lost`) skips all durable finalization; an edit-replay run (`metadata.replay_kind == "edit"`) that did not end `success` restores the pre-run checkpoint and republishes the restored `values` snapshot [Verified from source: worker.py:1013-1042, 1526-1548].
19. **Finally: flush + workspace changes + delivery receipt + terminal status** — order: flush `_SubagentEventBuffer`; `record_workspace_changes(event_store, ...)` (writes `workspace_changes` event, category `workspace`); `journal.flush()`; then `_persist_delivery_receipt()` — an idempotent `event_store.put_if_absent(event_type="run.delivery", category="outputs")` with bounded retries `(0.1, 0.5)` seconds; if produced outputs exist, a successful run whose receipt could not persist is downgraded to `error` with `_DELIVERY_RECEIPT_FAILED_ERROR`; only *then* the staged terminal status is durably persisted (`persist_current_status` on abort, else `set_status_if_not_cancelled`). This ordering closes the crash window where a terminal run could outlive its receipt [Verified from source: worker.py:1044-1113, 112-160, 163-164].
20. **Finally: completion data** — `journal.get_completion_data()` (token totals, per-model buckets, message count, first/last messages) → `run_manager.update_run_completion()` (only when `persist_completion` was set) [Verified from source: worker.py:1115-1121; runtime/journal.py:960-974].
21. **Finally: interrupted-title fallback** — for a non-edit-replay run that ended `interrupted`, after waiting for prior finalizers and only if no later run has started, `_ensure_interrupted_title()` derives a title via `TitleMiddleware._generate_title_result(..., allow_partial_exchange=True)` from the latest checkpoint (falling back to `graph_input` messages) and writes it as a raw `aput` checkpoint — parented to the checkpoint it derived from, with `channel_versions["title"]` bumped and declared in `new_versions` so DB-backed savers persist the blob; up to 3 optimistic retries on head movement [Verified from source: worker.py:1123-1129, 1999-2081, 1828-1870].
22. **Finally: title sync + run duration + thread status** — head checkpoint's `channel_values.title` synced to `thread_store.update_display_name()`; for successful runs, `duration = max(0, int(updated_at - created_at))` (whole RunRecord lifetime, incl. admission delay) merged into checkpoint metadata `run_durations` by `persist_run_durations()` — a metadata-only checkpoint (`writes = {"runtime_run_duration": {...}}`) written under `_checkpoint_thread_lock` with 3 optimistic retries, parented to the head; thread meta status becomes `"idle"` on success else the status value [Verified from source: worker.py:1131-1169, 1912-1996].
23. **Finally: hook + end** — `ctx.on_run_completed(record)` (non-fatal), `set_finalizing(False)`, `bridge.publish_end(run_id)`, then `bridge.cleanup(run_id, delay=60)` scheduled as a task [Verified from source: worker.py:1171-1180].

Supporting locks: `_checkpoint_thread_lock(thread_id)` is a per-event-loop, per-thread asyncio lock serializing checkpoint mutations (rollback capture, streaming, duration writes) without blocking goal commands (which use the separate `goal_thread_lock`) [Verified from source: worker.py:90-109; runtime/goal.py:59-82].

## 2. Checkpoint semantics

### Channel modes and freeze
- Two modes: `full` (whole-snapshot channel values) and `delta` (LangGraph `DeltaChannel` for `messages`: sentinel blobs + per-step writes) [Verified from source: runtime/checkpoint_mode.py:1-10].
- Mode is **process-frozen**: `freeze_checkpoint_channel_mode()` raises `CheckpointModeReconfigurationError` on a second different value; delta `snapshot_frequency` is frozen alongside (`freeze_checkpoint_snapshot_frequency`, must be positive, default from config `DEFAULT_CHECKPOINT_SNAPSHOT_FREQUENCY`), and is deliberately NOT stamped into checkpoint metadata [Verified from source: runtime/checkpoint_mode.py:39-78].

### Marker injection and compatibility gate
- `inject_checkpoint_mode(config, mode)` writes `configurable["__deerflow_checkpoint_channel_mode"]` always, and `metadata["deerflow_checkpoint_channel_mode"] = "delta"` in delta mode (popped in full mode). Absence of marker = full, so pre-feature checkpoints need no migration [Verified from source: runtime/checkpoint_mode.py:18-19, 81-88].
- Detection also honors upstream `metadata["counters_since_delta_snapshot"]["messages"]` [Verified from source: runtime/checkpoint_mode.py:91-98].
- **Asymmetric, fail-closed gate**: a full-mode process touching a delta thread raises `CheckpointModeMismatchError`; delta-mode processes read full checkpoints transparently (the gates short-circuit `if mode == "delta": return`). Writes are pre-checked (`ensure_checkpoint_mode_compatible` reads the head tuple); reads are checked post-fetch on the returned snapshot (`raise_if_snapshot_incompatible`) to avoid an extra fetch [Verified from source: runtime/checkpoint_mode.py:114-143].

### CheckpointStateAccessor
`CheckpointStateAccessor(graph, checkpointer, mode)` is the single choke point for thread-state access: every `get/aget/history/ahistory/update/aupdate` re-prepares the config (fresh `configurable`/`metadata` dicts), injects the mode marker, and applies the gate. Raw saver reads in delta mode see sentinels, so materialized reads must go through the bound compiled graph (`graph.get_state` etc.) [Verified from source: runtime/checkpoint_state.py:1-15, 111-196]. `bind()` attaches checkpointer/store onto the graph [Verified from source: runtime/checkpoint_state.py:117-129]. `history(limit=0)` returns `[]` explicitly (never passed through as unlimited) [Verified from source: runtime/checkpoint_state.py:152-174].

### State mutation graph
`build_state_mutation_graph(as_node, mode, state_schema)` compiles a one-node StateGraph (entry = finish, node returns `{}`) so `update_state(as_node=...)` can apply reducer writes while scheduling **no** pending agent nodes — the written head stays idle. `state_schema` must be the thread's *effective* schema (`graph_state_schema(assistant_graph)` = first entry of `builder.schemas`) or middleware-contributed channels are silently discarded [Verified from source: runtime/checkpoint_state.py:32-79]. `graph_writable_channels()` excludes `__*` and `branch:*`; `graph_reducer_channels()` = channels that are `BinaryOperatorAggregate` or `DeltaChannel` — both require `Overwrite` wrapping for replace-style writes [Verified from source: runtime/checkpoint_state.py:82-108].

### Rollback flow
- Capture: `_capture_rollback_point()` returns `None` for a thread with no checkpoint yet (rollback then means `adelete_thread` — reset to empty); in delta mode it deep-copies all non-message materialized values into `state_values` [Verified from source: runtime/runs/worker.py:1568-1599, 1747-1750].
- Restore (`_rollback_to_pre_run_checkpoint`): full mode **forks** from the captured pre-run checkpoint config, writing `{"messages": Overwrite(captured_messages)}`; other channels inherit from that parent. Delta mode cannot fork once the cancelled path attached sibling writes, so it **replaces every captured channel on the current head** via `_complete_state_replacement_values()`: selected channels deep-copied, head-only channels reset to their schema default (`channel.get()` when `is_available()`) or `None`, reducer channels wrapped in `Overwrite` [Verified from source: worker.py:1721-1801, 1602-1629].
- After the restore checkpoint is written, the captured raw `pending_writes` are re-attached, grouped by `task_id`, via `aput_writes` against the restored config; each entry must be a 3-tuple `(task_id, channel, value)` [Verified from source: worker.py:1803-1825].
- Fail-closed: capture failure (`snapshot_capture_failed`), missing checkpoint id, or missing accessor skip rollback entirely rather than restore partial state [Verified from source: worker.py:1743-1761].

### Linearized delta resume
Resuming from an older checkpoint is a fork; in delta mode `BaseCheckpointSaver.get_delta_channel_history` collects **every** `pending_writes` entry on each on-path ancestor, so a shared parent replays the abandoned sibling's writes into the fork (#4458). `_linearize_delta_checkpoint_resume()` therefore: no-ops for full mode / no `checkpoint_id` selector / non-root `checkpoint_ns` / selector == head; otherwise materializes the selected checkpoint's full state, builds a complete replacement (defaults for head-only channels), writes it onto the **current head** through a `checkpoint_resume` mutation graph, pops `checkpoint_id`/`checkpoint_map` from configurable, and returns the materialized messages. Failures propagate (falling back to the fork would persist corrupt history) [Verified from source: worker.py:1632-1718].

### Compatibility patches (`checkpoint_patches.py`)
Applied at import time (anchored from `agents/thread_state`) [Verified from source: checkpoint_patches.py:1-9, 191-192]:
- `ensure_inmemory_delta_history_patch()` — delegates `InMemorySaver.get_delta_channel_history` to the base walk because upstream's fused single-pass drops a checkpoint's own pending writes when the plain-value blob version was carried forward from an ancestor (first superstep after full→delta migration). Validated against langgraph `1.2.9`, warns on newer versions, stands down if the upstream override disappears [Verified from source: checkpoint_patches.py:27-100].
- `ensure_binop_overwrite_first_write_patch()` — probe-guarded fix for `BinaryOperatorAggregate.update` storing an `Overwrite` wrapper literally when it seeds an empty (MISSING) Union-typed channel (`sandbox`/`goal`/`todos`/`promoted` have no constructible default, #4380); intercepts only the empty-channel + leading-Overwrite case and mirrors upstream semantics (second Overwrite in the batch raises `InvalidUpdateError`) [Verified from source: checkpoint_patches.py:103-188].

### Manual raw writes must preserve parentage
All three worker/goal raw `aput` writers parent the new checkpoint to the tuple it was derived from — a parentless checkpoint "severs Delta-channel replay ancestry (and truncates history walks in full mode too)": goal writes [Verified from source: runtime/goal.py:524-535], run-duration metadata checkpoints [Verified from source: worker.py:1963-1979], interrupted-title checkpoints [Verified from source: worker.py:2065-2078]. DB-backed savers only persist blobs for channels listed in `new_versions`, so these writers bump `channel_versions[<ch>]` via `_bump_channel_version` (delegating to the saver's `get_next_version` with defensive fallbacks) and declare it [Verified from source: worker.py:1833-1870, 2047-2057].

### What LangGraph checkpoints actually guarantee here
- **Per-superstep snapshots**: the graph writes one checkpoint per superstep; `_stream_once` relies on that for abort semantics (breaking the stream leaves the last completed superstep durable) [Verified from source: worker.py:850-906 + design commentary at worker.py:2-13].
- **Parentage**: `parent_config` links form the lineage; forks are created by writing with a `checkpoint_id` selector (used by full-mode rollback) [Verified from source: worker.py:1785-1793].
- **Durability signal, not atomicity across turns**: `pending_writes` on the head tuple means a task's writes are queued but the turn is still in flight — `_has_durable_goal_turn_receipt()` requires a checkpoint id, empty `pending_writes`, and a visible trailing AI message before trusting the turn as durable ("a `CheckpointTuple` carries no `tasks` field... the presence of any queued writes is what tells us the turn is still in flight") [Verified from source: worker.py:1229-1246].
- **No cross-write transaction**: goal writes and metadata writes use optimistic checkpoint-id CAS (`GoalWriteConflict` when the head moved; 3-attempt retry loops in duration/title writers) rather than any store transaction [Verified from source: runtime/goal.py:496-500; worker.py:1936-1981, 2012-2035].

## 3. RunJournal / run events

### Event catalog (`runtime/events/catalog.py`) — ALL types
Fixed definitions (`event_type`, `category`); limits `event_type` ≤ 32 chars, `category` ≤ 16 chars [Verified from source: runtime/events/catalog.py:58-113; constants.py:15-21]:

| event_type | category | group |
|---|---|---|
| `run.start` | `trace` | journal |
| `run.end` | `outputs` | journal |
| `run.error` | `error` | journal |
| `llm.human.input` | `message` | journal |
| `llm.ai.response` | `message` | journal |
| `llm.tool.result` | `message` | journal |
| `llm.error` | `trace` | journal |
| `context:memory` | `context` | journal |
| `subagent.start` | `subagent` | subagent |
| `subagent.step` | `subagent` | subagent |
| `subagent.end` | `subagent` | subagent |
| `workspace_changes` | `workspace` | workspace |
| `middleware:{tag}` (pattern; known tags: `guardrail`, `safety_termination`, `skill_activation`, `skill_secrets`; tag ≤ 21 chars) | `middleware` | pattern |

Additionally, the terminal **`run.delivery`** event (category `outputs`) is written literally by the worker/recovery via `put_if_absent` (and by `RunJournal.record_delivery()` for direct journal users) — it is not a catalog constant [Verified from source: worker.py:130-138; journal.py:875-885; manager.py:987-1006].

### What gets persisted (`runtime/journal.py`)
`RunJournal` is a `BaseCallbackHandler` with `deerflow_loop_bound = True` (never copied into subagent isolated loops) and `run_inline = True` (callbacks stay on the run's event loop, serializing parallel tool callbacks) [Verified from source: journal.py:208-221]. Design decisions: no `on_llm_new_token` — only complete messages via `on_llm_end`; `on_chat_model_start` captures the first persistable human message as `llm.human.input` (structured, uncompressed); root `on_chain_start` (`parent_run_id=None`) emits `run.start`; root `on_chain_end` emits `run.end` (content = raw outputs, opaque) after reconciling final clarification ToolMessages; `on_chain_error` → `run.error`; `on_llm_end` → `llm.ai.response` (checkpoint-aligned `message.model_dump()` + metadata `caller`/`usage`/`latency_ms`/`llm_call_index`); `on_llm_error` → `llm.error`; `on_tool_end` persists `llm.tool.result` for ToolMessages (including those inside a `Command.update["messages"]`) and records produced artifacts when the command carries a non-empty `artifacts` update [Verified from source: journal.py:7-15, 312-562].

Hidden-message rule: `HumanMessage`s with `hide_from_ui=True` are persisted only when they carry an allowlisted `human_input_response` source (currently only `"ask_clarification"`); `name == "summary"` messages are never persisted [Verified from source: journal.py:51-64]. Clarification reconciliation: root-run `on_chain_end` re-persists allowlisted clarification ToolMessages (`_RECONCILED_TOOL_MESSAGE_NAMES = {"ask_clarification"}`) whose `tool_call_id` belongs to the current run and were not already persisted — needed because `ClarificationMiddleware` short-circuits before `on_tool_end` fires [Verified from source: journal.py:52, 609-635].

Caller identification: first tag matching `subagent:*`, `middleware:*`, or `lead_agent`; default `lead_agent` [Verified from source: journal.py:698-706]. Token accumulation: deduped by langchain run_id, bucketed by caller and per-model (sparse `cache_read_tokens` from `usage_metadata.input_token_details.cache_read`); `record_external_llm_usage_records()` merges subagent usage deduped by `source_run_id` [Verified from source: journal.py:483-512, 708-804]. `record_memory_context(content_sha256=...)` stores only the SHA-256 of the effective memory block, once per run [Verified from source: journal.py:832-847].

Buffering: `_put` appends to an in-memory buffer, flushed via fire-and-forget `put_batch` at `flush_threshold = 20` (or at root chain end/error); failed batches return to the buffer; `flush()` in the worker's finally drains everything and awaits pending tasks. Progress snapshots throttle at `progress_flush_interval = 5.0` s to `run_manager.update_run_progress` [Verified from source: journal.py:229-249, 637-696, 887-958].

### Seq ordering
The `RunEventStore` contract guarantees: put events retrievable, **seq strictly increasing within the same thread**, `list_messages()` returns only `category="message"`, `list_events()` returns all events for a run (with `event_types`/`task_id`/`after_seq` filters). `put_if_absent` is the idempotent per-(run, event_type) singleton write, serialized with ordinary thread writers — the durability primitive for terminal receipts [Verified from source: runtime/events/store/base.py:20-113]. The JSONL backend assigns seq from a per-thread in-process counter seeded by scanning existing files, under a per-thread asyncio lock; batches reserve all seqs and append in one file write so a retry cannot duplicate; single-process only (multi-process needs `DbRunEventStore`) [Verified from source: runtime/events/store/jsonl.py:5-21, 142-239].

### Subagent event buffering
`_SubagentEventBuffer` converts `task_*` custom stream chunks via `subagent_run_event()` and buffers recognized records, flushing with one `put_batch` per batch — eagerly on a terminal `subagent.end`, at `FLUSH_THRESHOLD = 25`, and in the worker's finally. Rationale: `RunEventStore.put` takes a per-thread advisory lock per call and a deep subagent (`max_turns=150`) emits hundreds of steps; failed flush batches are re-buffered ahead of newer events; missing store or unrecognized chunk is a no-op [Verified from source: worker.py:434-493, 834-837, 1044-1047].

## 4. Stream bridge (brief)

Contract (`runtime/stream_bridge/base.py`): producer calls `publish(run_id, event, data)` / `publish_end(run_id)`; consumer `subscribe(run_id, last_event_id=None, heartbeat_interval=15.0)` yields `StreamEvent(id, event, data)` items, `HEARTBEAT_SENTINEL` on idle timeout, `END_SENTINEL` (a `StreamEvent(id="", event="__end__")`) after `publish_end`, and a terminal `StreamGap(requested_event_id, earliest_available_event_id, latest_available_event_id)` then stops when the cursor has fallen behind retained history — the gap lets callers reload durable state without mistaking a partial replay for a complete one. `cleanup(run_id, delay)` releases resources after an optional grace delay; `supports_cross_process` defaults `False` [Verified from source: runtime/stream_bridge/base.py:16-91].

Memory implementation: per-run bounded event log (`queue_maxsize` default 256) with `{ts}-{seq}` ids where `seq` equals the absolute per-run offset (O(1) cursor resolution); overflow drops the oldest events and advances `start_offset`; a numeric cursor below the retained watermark yields a conservative gap, unknown ids at/above the watermark replay from earliest (legacy behavior); a live subscriber whose offset falls below `start_offset` also gets a gap and stops [Verified from source: runtime/stream_bridge/memory.py:27-180]. Redis variant adds cross-process streams with rolling TTL and atomic bounds+read snapshots (skimmed; see `runtime/stream_bridge/redis.py` and backend/AGENTS.md "Memory and Redis StreamBridge" notes).

## 5. Goal evaluation (`runtime/goal.py`)

- **Exact caps**: `DEFAULT_MAX_GOAL_CONTINUATIONS = 8`, `DEFAULT_MAX_NO_PROGRESS_CONTINUATIONS = 2`, `MAX_GOAL_OBJECTIVE_CHARS = 4000`, `MAX_GOAL_REASON_CHARS = 1000`, `MAX_GOAL_EVIDENCE_CHARS = 1000`, `MAX_GOAL_CONVERSATION_CHARS = 12000`, `MAX_GOAL_CONVERSATION_MESSAGES = 30` [Verified from source: runtime/goal.py:35-41]. `build_goal_state` clamps `max_continuations` to `max(0, min(requested, 8))` [Verified from source: runtime/goal.py:118-138].
- **Blocker taxonomy**: `GOAL_BLOCKERS = {"none", "missing_evidence", "needs_user_input", "run_failed", "external_wait", "goal_not_met_yet"}`; only `goal_not_met_yet` is continuable (`CONTINUABLE_GOAL_BLOCKERS`) [Verified from source: runtime/goal.py:43-51]. Blocker normalization: satisfied → `"none"`; unknown/`"none"` while unsatisfied → `"missing_evidence"` [Verified from source: runtime/goal.py:174-179].
- **Evaluator prompt approach**: a non-thinking chat model (`create_goal_evaluator_model`, `thinking_enabled=False`, `attach_tracing=True` because there is no graph root to inherit tracing from) receives a strict system instruction — "strict completion evaluator", judge ONLY visible conversation evidence, never assume external state changed, fail closed with `missing_evidence`, output exactly one JSON object `{"satisfied": boolean, "blocker": string, "reason": string, "evidence_summary": string}` — plus the goal objective and the last 30 visible messages (trailing 12000 chars). With no visible assistant evidence it short-circuits to `missing_evidence` without a model call. Response parsing strips think blocks/code fences and extracts the first `{...}` [Verified from source: runtime/goal.py:242-327, 141-165, 206-239].
- **Continuation gate**: `should_continue_goal` requires unsatisfied + continuable blocker + `continuation_count < max_continuations` + `no_progress_count < max_no_progress_continuations` [Verified from source: runtime/goal.py:330-340].
- **No-progress breaker**: keyed on `latest_visible_assistant_signature` (SHA-256 of the latest visible AI text — not the evaluator's reworded free text); `compute_no_progress_count` increments when the `progress_key` (satisfied + blocker + evidence signature JSON) matches the previous `last_evaluation.progress_key`, else resets to 0 [Verified from source: runtime/goal.py:343-388].
- **Stand-down reasons** (recorded into `goal.last_evaluation.stand_down_reason`): `blocked:{blocker}` (non-continuable blocker), `max_continuations_reached`, `no_progress_detected` [Verified from source: worker.py:1249-1260]; plus worker-side race/durability reasons: `no_durable_end_of_turn` (no durable assistant end-of-turn receipt), `thread_changed_after_evaluation`, `thread_changed_before_continuation` [Verified from source: worker.py:1403-1412, 1446-1450, 1499-1514].
- **Persistence semantics**: every non-satisfied evaluation is persisted via `_persist_goal_evaluation` under `goal_thread_lock` with checkpoint-id CAS (`write_thread_goal(expected_checkpoint_id=...)` raises `GoalWriteConflict` on movement) and streamed as a `values` frame; satisfied goals are cleared (`write_thread_goal(..., None)`); the continuation count is defensively recomputed inside the lock (`max(caller_count, current+1)`) [Verified from source: worker.py:1263-1318, 1452-1478; runtime/goal.py:474-536]. The hidden continuation input is a `HumanMessage` wrapped in `<goal_continuation>` with `additional_kwargs = {"hide_from_ui": True, "deerflow_goal_continuation": True}` [Verified from source: runtime/goal.py:391-408].
- Goal state lives in the checkpoint channel `goal` (`checkpoint["channel_values"]["goal"]`); reads/writes are raw checkpointer operations, parented and version-bumped [Verified from source: runtime/goal.py:462-536].

## 6. Interrupt / cancel / resume at runtime level

### Clarification interrupts
`ClarificationMiddleware` intercepts `ask_clarification` and interrupts via `Command(goto=END)` (documented middleware #35); at the runtime level this simply *ends the graph cleanly* — the run finishes through the normal success path, and the `__interrupt__` channel key is deliberately preserved in serialized `values` frames so the SDK can detect interrupts (`serialize_channel_values` strips only `__pregel_*`) [Verified from source: backend/AGENTS.md middleware chain item 35; runtime/serialization.py:59-71]. The reply arrives as a new run whose input is a `hide_from_ui` HumanMessage with `additional_kwargs.human_input_response`; `RunJournal` persists it as `llm.human.input` only for allowlisted sources (`ask_clarification`) [Verified from source: runtime/journal.py:53-64].

### Cancel
`RunManager.cancel(run_id, action="interrupt"|"rollback")` → `CancelOutcome` enum `{cancelled, requested, taken_over, lease_valid_elsewhere, not_cancellable, not_active_locally, unknown}` [Verified from source: manager.py:1187-1359, 2237-2247]. Local path: sets `abort_action`, `abort_event`, `finalizing`, cancels the task if running, stages `interrupted`, persists outside the lock; peer takeover detected post-persist returns `taken_over`. Non-local path (heartbeat on): live lease → durable `request_cancel` row (`runs.cancel_action`/`cancel_requested_at`, first action wins — consumed by the owner in `renew_lease`); expired lease → `claim_for_takeover` marks `error`. The worker observes the abort at the next stream chunk (`record.abort_event.is_set()` → break) and finalizes via `_finish_cancellation`: `interrupt` keeps the checkpoint (status `interrupted`), `rollback` restores the pre-run checkpoint and sets status `error` with `"Rolled back by user"` [Verified from source: worker.py:554-596, 859-861; manager.py:1099-1185, 1958-2069; persistence/run/model.py:52-55].

### multitask_strategy interrupt/rollback
Replacement admission cancels inflight predecessors: store-side rows are claimed+interrupted in the same transaction as the replacement insert (`create_thread_operation_atomic`), local in-memory inflight get `abort_action = strategy` (so the old worker's `_finish_cancellation` performs interrupt vs rollback), and the replacement then waits in `wait_for_prior_finalizing` before entering the graph. A caller cancelled during post-registration persistence triggers a shielded `_close_cancelled_admission` cleanup. Non-run thread operations (`checkpoint_write`/`artifact_write` reservations) block interrupt/rollback admission with `ConflictError` [Verified from source: manager.py:1446-1639, 1401-1444, 1505-1511; worker.py:618-622].

### Resume from checkpoint
Thread-scoped run creation may carry `configurable.checkpoint_id`/`checkpoint_map`; the worker validates mode compatibility for the selector [Verified from source: worker.py:653-669], and in delta mode rewrites the fork into a linear head write before streaming (§2, `_linearize_delta_checkpoint_resume`) while full mode forks natively. Goal continuation turns always drop the selector (`_continuation_runnable_config`) so hidden turns continue from the head [Verified from source: worker.py:744-751]. Resumed runs get their current-run message boundary recomputed from the resumed state (`pre_existing_message_ids`), which both scopes error-fallback detection and lets durable-context capture identify the request boundary when no new HumanMessage is appended [Verified from source: worker.py:788-807, 2120-2212].

### Crash / orphan recovery
Heartbeat renews leases every `lease_seconds/3`, fails closed at the last confirmed deadline (`ownership_lost` fence: abort + no further durable writes; the peer owns terminalization), and collects durable cancel actions; reconciliation (startup + every 3rd heartbeat cycle, single-flight) claims expired/NULL-lease active rows via atomic `claim_for_takeover`, marks them `error` with `stop_reason="orphan_recovered"`, and backfills a zero-delivery receipt via the same `put_if_absent` singleton — so an existing detailed receipt from a crashed-after-receipt worker is preserved [Verified from source: manager.py:33-35, 1700-1784, 1845-2069, 987-1006]. `shutdown(timeout)` aborts inflight tasks, drains them within the deadline so final checkpoints flush before checkpointer teardown, and marks only non-settled runs `interrupted` [Verified from source: manager.py:2136-2234].

## 7. Context compaction (`runtime/context_compaction.py`)

Manual `/compact` flow — `compact_thread_context(accessor, thread_id, *, keep=None, force=True, user_id, agent_name, model_name, app_config)`:
1. Resolve the summarization model mirroring lead resolution (explicit request model validated against configured models → thread's custom-agent configured model, loaded off-loop → `config.models[0]`) [Verified from source: runtime/context_compaction.py:71-96].
2. Build `DeerFlowSummarizationMiddleware` via `create_summarization_middleware`; `None` (summarization disabled) raises `ContextCompactionDisabled` [Verified from source: runtime/context_compaction.py:41-50].
3. Read the head snapshot through the accessor; missing `checkpoint_id` raises `LookupError`; empty/absent messages return `ThreadCompactionResult(compacted=False, reason="not_enough_messages")` [Verified from source: runtime/context_compaction.py:115-125].
4. Call `middleware.acompact_state({messages, summary_text}, runtime, force=force, raise_on_failure=True)`; a `SummaryGenerationError` maps to `ContextCompactionFailed` (HTTP 500 path), distinct from `None` ("nothing to compact") [Verified from source: runtime/context_compaction.py:127-149].
5. Write the compacted state through the accessor: `accessor.aupdate(snapshot.config, {"messages": Overwrite(preserved_messages), "summary_text": result.summary_text}, as_node="manual_compaction")` — i.e. through the state mutation machinery, bumping only those channels; result includes removed/preserved counts, new `checkpoint_id`, `total_tokens` [Verified from source: runtime/context_compaction.py:151-169].

Concurrency: the Gateway route wraps this in `reserve_checkpoint_write()` (process-local thread lock + durable `checkpoint_write` thread-operation reservation), so compaction is blocked while a run is inflight and blocks new run admission across workers [Verified from source: manager.py:1641-1698; backend/AGENTS.md "Gateway checkpoint mutations outside run execution"].

## 9. Port-relevant observations

**Guarantees a Claude Code port must reproduce** (they carry correctness, not just plumbing):

1. **Checkpoint identity + parentage.** Every state write must (a) parent to the checkpoint it was derived from and (b) advance channel versions for exactly the channels written — DeerFlow treats a parentless or version-less write as corruption (severed delta ancestry, dropped blobs) [Verified from source: runtime/goal.py:524-535; worker.py:2044-2078]. A port keeping conversation state in files/SDK sessions must preserve an equivalent lineage identity (which snapshot a resume/rollback/branch anchors to) and an equivalent "settled head" notion.
2. **Staleness detection via optimistic CAS on the head id.** All out-of-band mutations (goal writes, duration/title metadata, goal-loop continuation) compare the head `checkpoint_id` read before the decision with the head at write time and stand down/retry on movement [Verified from source: runtime/goal.py:496-500; worker.py:1398-1450, 1936-1954, 2027-2035]. The port needs the same compare-and-stand-down primitive for any state it mutates while an agent might be running.
3. **Resume inputs / current-run boundary.** A resumed or continued run may append no new user message; the "what belongs to *this* run" boundary is the pre-run message-id set (`__deerflow_pre_run_message_ids`), recomputed after a resume rewrite. It gates both error-fallback attribution (one stale fallback marker must not poison later runs) and delegation-ledger boundaries [Verified from source: worker.py:528-532, 785-807, 2120-2212].
4. **Rollback = restore captured materialized state, fail-closed.** Rollback restores a *materialized* pre-run capture (messages + non-message channels + raw pending writes), never a raw blob copy, and is disabled entirely when capture failed — restoring partial history is worse than not restoring [Verified from source: worker.py:765-786, 1551-1599, 1721-1825]. A port should capture its rollback point eagerly (before the run mutates anything) under the same lock that serializes run streaming.
5. **Delta-fork poisoning (if the port has any delta/append-log state).** Resuming from a non-head snapshot in an append-log representation replays the abandoned sibling's writes; DeerFlow's fix is "linearize onto the head with replace semantics, drop the selector" [Verified from source: worker.py:1632-1718]. Any port with incremental transcript storage must either make writes child-owned or linearize forks the same way.
6. **Receipt-before-status ordering.** The terminal delivery receipt is an idempotent singleton write (`put_if_absent` keyed on `(run_id, event_type)`) persisted *before* the staged terminal status, with a crash-recovery path that backfills a zero receipt only after atomically claiming the run — this pair is what makes "did this run present its artifacts" crash-safe [Verified from source: worker.py:1061-1113; manager.py:987-1006, 1773-1780]. A port needs the same idempotent-singleton + ordering discipline for any "run produced X" fact.
7. **Durable end-of-turn receipt before autonomous continuation.** The goal loop refuses to continue unless the head checkpoint has an id, no pending writes, and a visible trailing assistant message [Verified from source: worker.py:1229-1246, 1403-1412]. Ports running autonomous continuation loops need an equivalent "turn is durably complete" predicate.
8. **Exact goal-loop caps and breaker semantics**: continuation cap hard-max 8 (clamped), no-progress breaker 2, keyed on the SHA-256 of the latest visible assistant text — not evaluator prose [Verified from source: runtime/goal.py:35-36, 343-359].
9. **Ownership fencing.** Once lease ownership cannot be confirmed, the local worker performs *no* further durable writes (status, receipts, checkpoints, thread meta) — the peer reconciler owns terminalization; `update_run_completion` refuses to replace a different terminal status [Verified from source: worker.py:1013-1018 and each `record.ownership_lost` guard; manager.py:1845-1881; runtime/runs/store/base.py:183-189]. Single-process ports can collapse this to "startup reclaims NULL-lease active rows" (the heartbeat-off behavior) [Verified from source: manager.py:1361-1374].
10. **Event feed identity**: `run_id` is a *turn identity* to feed consumers (regenerate supersedes a whole run_id), and seq is strictly increasing per thread — both are contracts consumers rely on [Verified from source: runtime/journal.py:97-127; runtime/events/store/base.py:25-30].

**HTTP-serving / deployment concerns a port can drop or simplify:**

- The `StreamBridge` (SSE ids, `Last-Event-ID` replay, `StreamGap`, heartbeats, Redis cross-process fan-out, `cleanup(delay=60)`) exists to decouple producers from SSE consumers; an in-process port that renders directly can replace it with a plain callback, keeping only the END semantics for "run finished" [Verified from source: runtime/stream_bridge/base.py:53-91].
- Multi-worker machinery — leases/heartbeat, durable cancel handoff (`runs.cancel_action`), `claim_for_takeover`, thread-operation reservations, the partial unique index — is cross-process admission control; a single-process port needs only the in-memory equivalent (one active operation per thread, interrupt/rollback cancels predecessors before the replacement enters the graph) [Verified from source: manager.py:1099-1359, 1446-1698].
- The `_LargeFileToolChunkBatcher` (batch 32) exists to protect browser JSON reparsing of streamed file bodies; irrelevant off the web [Verified from source: worker.py:226-344].
- Mode markers/compatibility gate matter only if two representations of the same thread store can coexist across process generations; a port with a single storage format needs only the version stamp + fail-closed read.
- `serialize()`'s API hygiene (stripping `__pregel_*`, dropping base64 `data:` image blocks from `hide_from_ui` messages, preserving `__interrupt__`) is wire-format concern, but the *categories* (hidden messages, interrupt payloads) map to port-side display filtering [Verified from source: runtime/serialization.py:59-146].
