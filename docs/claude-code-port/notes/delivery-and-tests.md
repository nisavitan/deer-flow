Source-analysis note for the Claude Code port plan. Scope: gateway / channels / scheduler / TUI / frontend (the DELIVERY layer) and the full `backend/tests/` suite, to support the engine-vs-delivery boundary decision. Companion to the engine-side notes.

## 1) Gateway structure, and which lifecycle logic lives in gateway vs harness

### 1.1 Layout

`backend/app/gateway/` is a FastAPI app (port 8001) with 24 routers plus auth, CSRF, trace-correlation, and authorization middleware:

- `app.py` (680 lines) — `create_app()` + lifespan.
- `services.py` (1448 lines) — the run-lifecycle service layer routers delegate to.
- `routers/` (24 modules): `agents`, `artifacts`, `assistants_compat`, `auth`, `browser`, `channel_connections`, `channels`, `console`, `features`, `feedback`, `github_webhooks`, `input_polish`, `integrations` (Lark), `mcp`, `memory`, `models`, `runs` (stateless), `scheduled_tasks`, `skills`, `suggestions`, `thread_runs`, `threads`, `uploads`.

### 1.2 LangGraph runtime embedding

The lifespan wraps everything in `async with langgraph_runtime(app, startup_config)` from `app/gateway/deps.py` [Verified from source: backend/app/gateway/app.py:284-332]. `langgraph_runtime` (an `@asynccontextmanager`, `deps.py:347+`) constructs and parks on `app.state`: frozen `checkpoint_channel_mode` / `checkpoint_snapshot_frequency`, `stream_bridge`, `checkpointer`, `store`, `run_store` (SQL `RunRepository` or `MemoryRunStore`), `feedback_repo`, `thread_store`, `scheduled_task_repo`/`scheduled_task_run_repo`, `run_events_config` + `run_event_store`, and `run_manager` (with orphan-run reconciliation and heartbeat start) [Verified from source: backend/app/gateway/deps.py:389-490]. So the "LangGraph server" is not a separate service — the harness runtime (`deerflow.runtime`) is embedded in-process and nginx merely rewrites `/api/langgraph/*` onto the gateway's native routes.

After the runtime is up, the lifespan starts the IM channel service (`start_channel_service(startup_config, get_stream_bridge=lambda: app.state.stream_bridge)`) and the `ScheduledTaskService` (with `launch_run=lambda **kw: launch_scheduled_thread_run(app=app, **kw)`) [Verified from source: backend/app/gateway/app.py:292-330]. Shutdown drains channels, scheduler, browser sessions, and the memory queue with bounded timeouts [app.py:334-438].

### 1.3 Lifecycle logic: gateway vs harness split

This is the key boundary finding: **the gateway owns admission/HTTP concerns; every piece of agent lifecycle mechanics is imported from the harness (`deerflow.runtime.*`)**.

- **Worker invocation**: `services.start_run()` validates thread id + legacy secret carriers, validates model allowlist, enforces thread ownership, builds the RunnableConfig (`build_run_config` + `merge_run_context_overrides` + `inject_authenticated_user_context` — trust-boundary scrubbing of `is_internal`, `authz_attributes`, `channel_user_id`, `langgraph_auth_user*`, `__`-prefixed context keys), admits via `run_mgr.create_or_reject(...)`, then attaches a task whose body calls the harness `run_agent(bridge, run_mgr, record, ctx, agent_factory, graph_input, config, stream_modes, ...)` [Verified from source: backend/app/gateway/services.py:1050-1267]. `run_agent`, `RunManager`, `StreamBridge`, `END_SENTINEL`/`HEARTBEAT_SENTINEL`, `ConflictError` all come from `deerflow.runtime` [services.py:38-55]. The actual run worker (streaming, journaling, rollback, delivery receipts, title fallback, subagent event persistence) is `deerflow/runtime/runs/worker.py` — harness, not gateway.
- **Goal loop**: entirely harness. `runtime/goal.py` owns `evaluate_goal_completion`, continuation messages, `goal_thread_lock`, and `runtime/runs/worker.py` drives the hidden-continuation loop (`evaluate_goal_completion` called at worker.py:1417) [Verified from source: backend/packages/harness/deerflow/runtime/runs/worker.py:51-68,1417; goal.py:270]. The gateway only exposes goal CRUD (`GET/PUT/DELETE /threads/{id}/goal` in `routers/threads.py`, importing `read_thread_goal`/`write_thread_goal`/`build_goal_state` from `deerflow.runtime.goal`) [Verified from source: backend/app/gateway/routers/threads.py:58-63]. The TUI/embedded client reach the same goal logic through `DeerFlowClient.get_goal/set_goal/clear_goal` [Verified from source: backend/packages/harness/deerflow/client.py:527-553].
- **Compaction route**: `POST /threads/{id}/compact` is a thin route over harness `deerflow.runtime.context_compaction.compact_thread_context`, serialized through the gateway-composed `reserve_checkpoint_write()` (process-local `goal_thread_lock` + durable `RunManager.reserve_thread_operation(kind=checkpoint_write)`) [Verified from source: backend/app/gateway/routers/threads.py:42,52-56,1145-1188; services.py:79-94]. The summarization logic itself is the same `DeerFlowSummarizationMiddleware` the engine uses.
- **Branching / regenerate**: this is the one lifecycle area with real gateway-resident logic: `app/gateway/checkpoint_lineage.py` (parent-lineage walk, settled-checkpoint gate, fail-closed integrity errors) plus branch/regenerate/edit-replay preparation in `routers/threads.py` / `routers/thread_runs.py` (pre-user replay anchor materialization, branch history seeding into `run_events`, workspace best-effort clone). It builds on harness primitives (`CheckpointStateAccessor`, `build_state_mutation_graph`, `inject_checkpoint_mode`) exposed via `services.build_checkpoint_state_accessor` / `build_checkpoint_state_mutation_accessor` [Verified from source: backend/app/gateway/services.py:657-927]. Delta-mode fork linearization, however, is harness (`worker.py::_linearize_delta_checkpoint_resume`).
- **SSE**: `services.format_sse`, `sse_consumer` (LangGraph-Platform wire format, gap/heartbeat/end handling, `on_disconnect` semantics) and `wait_for_run_completion` are gateway-side but purely transport [Verified from source: backend/app/gateway/services.py:120-133,1325-1448].
- **Other gateway-resident behaviors**: startup admin bootstrap + orphan-thread migration [app.py:68-174], legacy checkpoint-history seeding (`ensure_checkpoint_history_seeded`, a documented migration shim) [services.py:988-1042], recursion-limit clamping [services.py:501-533], degraded raw-checkpoint read accessor for a broken agent factory (full mode only) [services.py:731-805], accessor-graph cache [services.py:706-728].

Port implication: the engine boundary in the code is already `deerflow.runtime` + `deerflow.agents` + `deerflow.client`. The gateway adds auth/trust scrubbing, SSE transport, branching/regeneration preparation, and migration shims — all replaceable delivery concerns.

## 2) TUI: proof the engine runs without the gateway

`backend/packages/harness/deerflow/tui/` is a Textual UI **inside the harness package** — it never imports `app.*` and never speaks HTTP.

- **Session construction**: `open_session()` builds `DeerFlowClient(checkpointer=get_checkpointer())` directly from `deerflow.client` and `deerflow.runtime.checkpointer.provider` — no server, no SDK client [Verified from source: backend/packages/harness/deerflow/tui/session.py:84-103]. Thread resolution (`--continue`/`--resume` by id or title) goes through `client.list_threads()` [session.py:27-67].
- **Run invocation**: the Textual app runs `stream_actions(self.session.client, text, thread_id=thread_id, model_name=...)` on a worker thread; `stream_actions` drives the synchronous generator `client.stream(...)` and brackets it with `RunStarted`/`RunEnded`, converting exceptions to an `AssistantError` row [Verified from source: backend/packages/harness/deerflow/tui/app.py:565-603; runtime.py:99-114]. `translate()` maps `StreamEvent` types (`messages-tuple`, `values`, `end`) to pure reducer actions [runtime.py:41-89]. Headless mode is even more direct: `--print` calls `session.client.chat(message, thread_id=...)`, `--json` iterates `session.client.stream(...)` and prints NDJSON [Verified from source: backend/packages/harness/deerflow/tui/cli.py:191-214].
- **State**: `view_state.py` is a pure immutable reducer (rows: user/assistant/tool/system; delta merge semantics for cumulative re-sends vs incremental deltas; anonymous-row tracking for id-less provider chunks) [Verified from source: backend/packages/harness/deerflow/tui/view_state.py:167-390].
- **Feature parity through the client, not HTTP**: model picker (`client.list_models`), skills (`client.list_skills`), MCP (`client.get_mcp_config`), memory (`client.get_memory`), uploads (`client.list_uploads`), goals (`client.get_goal/set_goal/clear_goal` — the same `runtime/goal.py` state the gateway routes use) [Verified from source: backend/packages/harness/deerflow/tui/app.py:416-561,471-507].
- **Web-UI visibility without the gateway**: `persistence.py`'s `ThreadMetaWriter` writes `threads_meta` rows through the harness-only `deerflow.persistence.engine` on a background loop, so TUI threads appear in the Web sidebar with no gateway process involved [app.py:585-603; session.py:69-103].

Conclusion for the port: **DeerFlowClient is a complete, HTTP-free engine facade** (chat, streaming, goals, skills, MCP, memory, uploads, artifacts, checkpointer persistence). Any port that reproduces the engine behind a `DeerFlowClient`-shaped interface keeps the TUI and headless CLI working unchanged, and the gateway is demonstrably optional.

## 3) Channels, scheduler, integrations, tracing

### 3.1 `backend/app/channels/` (one paragraph per file, structure level)

- `__init__.py` — package docstring: pluggable channel system bridging Feishu/Slack/Telegram/etc. to the agent via `ChannelManager`, which talks to the gateway through `langgraph-sdk` HTTP (channels are gateway *clients*, not engine callers).
- `base.py` (199) — abstract `Channel` base class: start/stop/send lifecycle, `receive_file` hook.
- `commands.py` (89) — the single authoritative slash-command set (`/new`, `/help`, `/status`, `/models`, `/memory`, `/goal`, ...) shared by all channel parsers and the manager dispatcher.
- `connection_identity.py` (44) — attaches persisted channel-connection ownership (`connection_id`, `owner_user_id`, `workspace_id`) to `InboundMessage`s.
- `dedupe_store.py` (276) — inbound webhook dedupe store; in-process `OrderedDict` default plus a shared multi-pod variant.
- `manager.py` (2445) — the core dispatcher: thread lookup/create via SDK, command routing, `runs.wait` vs `runs.stream` vs fire-and-forget `runs.create` per `ChannelRunPolicy`, same-thread serialization, follow-up buffering while busy (GitHub), owner-scoped file storage, artifact delivery.
- `message_bus.py` (193) — async pub/sub hub decoupling channels from the dispatcher (`InboundMessage` queue → dispatcher; `OutboundMessage` → channel callbacks); carries transient inbound file bytes.
- `run_policy.py` (118) + `feishu_run_policy.py` (15) — global `CHANNEL_RUN_POLICY` registry (`serialize_thread_runs`, `fire_and_forget`, `buffer_followups_on_busy`) with per-channel registration side-effect modules.
- `runtime_config_store.py` (157) — local JSON persistence for runtime IM channel configuration edits.
- `service.py` (462) — `ChannelService`: lifecycle of all configured channels from `config.yaml`, started/stopped by the gateway lifespan.
- `store.py` (153) — `ChannelStore`: JSON persistence of `channel:chat[:topic]` → `thread_id` mappings.
- Platform adapters: `feishu.py` (1157, WebSocket + card patching), `slack.py` (441, Socket Mode), `telegram.py` (892, long-poll + in-place `editMessageText` streaming + attachments), `discord.py` (643), `dingtalk.py` (1095, AI Card streaming + file download), `wechat.py` (1477, iLink long-poll), `wecom.py` (470), `github.py` (115, webhook-driven, log-only outbound — agents post via `gh` from the sandbox).

Port relevance: channels are pure delivery. They reach the engine only through the gateway's LangGraph-compatible HTTP API (internal auth + CSRF pair), so a port that preserves that HTTP contract keeps every channel; a port that drops HTTP must re-home the SDK calls.

### 3.2 `backend/app/scheduler/`

`service.py` (530): `ScheduledTaskService` — polls `scheduled_tasks` on an interval under a global `max_concurrent_runs` budget, claims due tasks with hostname+uuid leases, and dispatches each through the injected `launch_run` closure (= `services.launch_scheduled_thread_run`, which builds an internal `RunCreateRequest` with `context={"non_interactive": True, "user_id": owner}` and calls the same `start_run` path as HTTP) [Verified from source: backend/app/scheduler/service.py:25-120; backend/app/gateway/services.py:1273-1322]. Careful status semantics for once vs cron tasks, manual vs scheduled triggers, and overlap conflicts (DB partial unique index is the atomic arbiter). Schedule math is delegated to the harness (`deerflow.scheduler.schedules`).

### 3.3 `backend/packages/harness/deerflow/scheduler/schedules.py`

Pure schedule computation (59 lines): `validate_timezone`, `normalize_cron_expression` (exactly 5 fields), and `next_run_at(schedule_type, spec, tz, now)` — `once` (naive run_at interpreted as wall clock in task tz, normalized to UTC for tz-discarding columns) and `cron` (croniter in local tz → UTC) [Verified from source: backend/packages/harness/deerflow/scheduler/schedules.py:9-59]. No I/O; trivially portable.

### 3.4 `backend/packages/harness/deerflow/integrations/`

Managed first-party Lark/Feishu CLI integration: `lark_cli.py` (1724) installs the official `lark-*` skill pack into a global read-only integration skill directory, manages per-user credentials/OAuth device flow, sandbox runtime provisioning modes (gateway-download / init-container / broker) and status reporting; `lark_broker.py` (457) is the Pattern-B sidecar credential broker that removes plaintext credential mounts from the sandbox (forwards the `lark-cli` command surface over Pod loopback). Delivery-adjacent (driven by the gateway `integrations` router) but lives in the harness because skill installation is an engine-side concern.

### 3.5 `backend/packages/harness/deerflow/tracing/`

Observability wiring, three providers: `factory.py` (65) returns LangChain callback handlers for LangSmith/Langfuse attached at the graph invocation root; `metadata.py` (114) builds Langfuse reserved trace attributes (`langfuse_session_id` = thread, `langfuse_user_id`, `langfuse_trace_name`, tags, `deerflow_trace_id`); `monocle.py` (69) is a one-shot process-global OTel/Monocle setup called only from the gateway lifespan (embedded/TUI paths are intentionally uninstrumented unless the caller opts in). Cross-cutting infra, not engine behavior.

## 4) Frontend (structure only)

`frontend/` is a Next.js (App Router) + pnpm workspace: `src/app` ( `(auth)`, `[lang]` localized pages, `api`, `workspace`, `blog`, `mock`), `src/core` (domain modules: `agents`, `api`, `artifacts`, `auth`, `channels`, `citations`, `config`, `features`, `i18n`, `input-polish`, `integrations`, `mcp`, `memory`, `messages`, `models`, `notification`, `scheduled-tasks`, `settings`, `sidecar`, `skills`, `streamdown`, `suggestions`, `tasks`, `threads`, `todos`, `tools`, `uploads`, `voice-input`, `workspace-changes`), plus `components`, `hooks`, `lib`, `styles`, `content`. It talks to the backend exclusively through nginx (`NEXT_PUBLIC_LANGGRAPH_BASE_URL=/api/langgraph`, REST at `/api/*`) using the LangGraph SDK `useStream` hook for runs. Four Playwright configs (`playwright.config.ts`, `.auth`, `.real-backend`, `.record`) plus `rstest.config.ts` for unit tests. Entirely delivery; port-relevant only as a consumer of the LangGraph-Platform-compatible SSE/REST contract (SSE frame format, `Content-Location` run id header, run-event feed, subagent `task_*` custom events).

## 7) Port-relevant observations

1. **The engine/delivery seam already exists and is CI-enforced.** `tests/test_harness_boundary.py` guarantees `deerflow.*` never imports `app.*`. The gateway consumes the engine exclusively through `deerflow.runtime` (`run_agent`, `RunManager`, `StreamBridge`, `CheckpointStateAccessor`, goal/compaction helpers) and `make_lead_agent`. A port can treat that import surface as the engine API.
2. **The TUI is the existence proof for gateway-free operation** (§2): `DeerFlowClient(checkpointer=...)` + `client.stream()` runs the full agent (middleware chain, subagents, skills, memory, goals) with zero HTTP. `client.py` is therefore the minimal engine facade to reproduce first.
3. **Lifecycle logic that a port must NOT look for in the gateway**: run worker/streaming/rollback/journal, goal continuation loop, compaction, delta-mode linearization, subagent execution — all harness. Gateway-resident logic worth porting deliberately: trust-boundary scrubbing of run configs (`services.py` — server-owned context keys, `__`-prefix stripping, recursion-limit clamp, secret redaction), checkpoint lineage walking for branch/regenerate, SSE framing + gap/heartbeat semantics, migration shims (checkpoint-history seeding, orphan-thread migration).
4. **Delivery consumers pin two wire contracts**: (a) LangGraph-Platform-compatible SSE (`format_sse` field order, `end`/`gap` events, `Content-Location` run id — the stock `langgraph-sdk` default payload is itself a pinned test, `test_run_request_validation::test_gateway_accepts_langgraph_sdk_default_payload`); (b) the run-event store feed (`contracts/run_event_stream_contract.json`, `test_run_event_stream_contract.py`) that the frontend thread view and branch seeding read. Channels and frontend both depend on (a); frontend history depends on (b).
5. **Test-suite shape supports a parity-first port**: engine-behavior tests dominate (~55% of files) and most middleware tests are pure-unit (fake models, no network). The seven deep-read files in §6 (~9,900 lines combined) plus `test_thread_state_reducers`, `test_subagent_limit_middleware`, `test_deferred_*`, `test_goal_runtime`/`test_goal_worker`, and `test_context_compaction` form the core parity spec. `test_build_lead_runtime_middlewares_chain_order_matches_agents_md` pins the exact middleware order documented in AGENTS.md — a single anchor to validate a ported chain against.
6. **Live/optional tiers are clearly separated**: `*_live` tests are opt-in (`DEER_FLOW_RUN_LIVE_TESTS=1`), `blocking_io/` is a Blockbuster runtime gate, `monocle/` is isolated, replay fixtures (`fixtures/replay`, `test_replay_golden.py`) offer a deterministic scripted-model harness a port could reuse for cross-implementation golden comparisons.
7. **Scheduler and channels reuse the run lifecycle rather than forking it** — scheduler dispatches through the same `start_run` (internal auth + `non_interactive`), channels through the same HTTP API the frontend uses. A port that keeps `start_run` semantics keeps both for free; the only channel-specific engine hooks are `channel_user_id`/`github_token`/`disable_clarification` runtime-context keys and the `original_user_content` provenance rules.
