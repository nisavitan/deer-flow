# Engine Boundary — DeerFlow → Claude Code Port

- **Commit:** `095092418ccf072aa866c0a663c4056c206091e5` (branch `port/claude-code-architecture`)
- **Date:** 2026-08-01
- **Inputs:** `notes/delivery-and-tests.md`, `notes/lead-agent-and-state.md`, `notes/runtime-and-persistence.md`, `repository-inventory.md` (all at this commit)

This document draws the line between **the DeerFlow engine** (behavior that must survive the port) and **delivery infrastructure** (replaceable by Claude Code's own transport, UI, and persistence). Every judgment is tagged `[Verified from source]` (the cited note verified it against code at this commit) or `[Inference]` (a boundary decision derived from verified facts, not itself pinned in code).

## Key anchor: the engine already runs without HTTP

The TUI is the existence proof. `backend/packages/harness/deerflow/tui/` builds `DeerFlowClient(checkpointer=get_checkpointer())` directly and drives `client.stream(...)` — no gateway process, no SSE, no SDK client. The full agent (middleware chain, subagents, skills, memory, goals, uploads, MCP) runs through the client facade, and TUI threads even appear in the Web sidebar via a harness-only `threads_meta` writer. "DeerFlowClient is a complete, HTTP-free engine facade … the gateway is demonstrably optional." [Verified from source: notes/delivery-and-tests.md §2, §7.2]

The seam is CI-enforced: `tests/test_harness_boundary.py` guarantees `deerflow.*` never imports `app.*`, and the gateway consumes the engine exclusively through `deerflow.runtime` (`run_agent`, `RunManager`, `StreamBridge`, `CheckpointStateAccessor`, goal/compaction helpers) and `make_lead_agent`. [Verified from source: notes/delivery-and-tests.md §7.1] The port target is therefore that import surface — reproduce the engine behind a `DeerFlowClient`-shaped interface, and everything above it is replaceable.

All harness paths below are relative to `backend/packages/harness/deerflow/`.

## C. Gray zone — lifecycle logic at the delivery seam that MUST still be ported

These live in the run worker / gateway (code invoked by the delivery layer, mostly harness `runtime/runs/worker.py`) but carry engine correctness. For each: what is kept vs dropped.

**C1. Run worker's goal-continuation loop** (`runtime/runs/worker.py` + `runtime/goal.py`).
- **Kept:** the entire loop — post-turn evaluation, hidden `<goal_continuation>` turns from the head (selector dropped), durable end-of-turn receipt gate (checkpoint id + no pending writes + visible trailing AI message), exact caps (8 continuations clamped, no-progress breaker 2 keyed on assistant-text SHA-256), stand-down reasons, CAS-guarded goal persistence, stale-`stop_reason` clearing only before the first visible turn. [Verified from source: notes/runtime-and-persistence.md §1 step 15, §5, §9.7–9.8]
- **Dropped:** `goal_thread_lock`-vs-gateway-route coordination and the streamed `values` frame for the evaluation (transport). [Inference]

**C2. Rollback capture** (`worker.py` `_capture_rollback_point` / `_rollback_to_pre_run_checkpoint`).
- **Kept:** eager pre-run capture of *materialized* state (messages + non-message channels + pending writes) under the same lock that serializes run streaming; fail-closed (capture failure disables rollback entirely); rollback-on-cancel (`action="rollback"` → restore + status error "Rolled back by user"); edit-replay restore on non-success; `pre_existing_message_ids` as the current-run boundary. [Verified from source: notes/runtime-and-persistence.md §1 steps 10, 17–18, §2 rollback, §9.3–9.4]
- **Dropped:** the delta-mode-specific dual strategy (fork vs head-replacement) and delta-resume linearization *as such* — the port keeps only the invariant behind them: never resume/rollback in a way that replays an abandoned sibling's writes; use replace semantics onto a single head. [Verified invariant: notes/runtime-and-persistence.md §9.5; drop decision: Inference]

**C3. Title fallback** (`worker.py` `_ensure_interrupted_title` + title sync).
- **Kept:** the behavior — an interrupted run still gets a derived thread title (from the partial exchange) unless a later run has started, and the state-side title is synced to the thread listing.
- **Dropped:** the raw-`aput` checkpoint mechanics (parentage, `channel_versions["title"]` bump, 3-retry CAS) — replaced by whatever atomic metadata write the port's session store offers, preserving the "stand down if the head moved / a later run started" guard. [Verified from source: notes/runtime-and-persistence.md §1 steps 21–22; split decision: Inference]

**C4. Workspace-changes scan + delivery receipts** (behavioral essence only) (`workspace_changes/**`, worker steps 6, 16, 19).
- **Kept:** pre-run snapshot → post-run diff; the delivery verdict (produced outputs not covered by `present_files` → run marked incomplete-delivery error); the idempotent-singleton "run produced X" receipt persisted *before* the terminal status, with successful-but-receiptless runs downgraded. [Verified from source: notes/runtime-and-persistence.md §1 steps 6, 16, 19, §9.6]
- **Dropped:** the `run_events` store row format, `put_if_absent` DB primitive, orphan-recovery zero-receipt backfill for crashed *peer* workers (single-process port: startup reclaim only), and the frontend workspace-changes endpoint/UI. [Verified basis: notes/runtime-and-persistence.md §9.9 drop-list; Inference on the exact cut]

**C5. Manual compaction flow** (`runtime/context_compaction.py`, gateway `POST /threads/{id}/compact`).
- **Kept:** the harness flow — same `DeerFlowSummarizationMiddleware` as auto-compaction, `force=True` with `raise_on_failure` (failure is an error, distinct from "nothing to compact"), preserved-message write + `summary_text` through the state-mutation path, and mutual exclusion with an inflight run (compaction blocked while running, and blocks new admission). [Verified from source: notes/runtime-and-persistence.md §7; notes/delivery-and-tests.md §1.3]
- **Dropped:** the HTTP route, `reserve_checkpoint_write()`'s durable cross-worker reservation (process-local exclusion suffices single-process). [Inference]

**C6. Branch / regenerate lineage semantics** (gateway `checkpoint_lineage.py` + prepare routes; harness `CheckpointStateAccessor`, `build_state_mutation_graph`, worker linearization).
- **Decision: port the core, defer the HTTP-specific parts.** [Inference]
- **Kept (core):** regenerate supersedes a whole `run_id` (run_id is a turn identity); branching anchors to an explicit lineage identity (parent-lineage walk, settled-checkpoint gate, fail-closed on integrity errors); replay-anchor semantics for edit-regenerate; state mutations go through reducer-aware machinery so middleware channels are not silently discarded. [Verified from source: notes/delivery-and-tests.md §1.3; notes/runtime-and-persistence.md §2, §9.1, §9.10]
- **Deferred/dropped:** the two-step HTTP `prepare` endpoints, branch history seeding into the `run_events` feed, workspace best-effort clone, and the degraded raw-checkpoint accessor for a broken agent factory — all serve the web UI's history views; revisit if the port grows an equivalent history surface. [Inference from notes/delivery-and-tests.md §1.3]

**C7. Scheduled `non_interactive` flag semantics**.
- **Kept:** the engine semantics — `context.non_interactive=true` removes `ask_clarification` from the lead toolset (`_NON_INTERACTIVE_DISABLED_TOOL_NAMES`), and the flag is honored only from a trusted internal launch path, never from client-supplied context (trust-boundary scrub). This must hold for any future mapping onto Claude Code's native scheduled agents. [Verified from source: notes/lead-agent-and-state.md §1 step 11, §8; notes/delivery-and-tests.md §3.2; AGENTS.md scheduled-task note]
- **Dropped:** the polling `ScheduledTaskService`, task leases, and the scheduled-tasks router/page (see B, scheduler row). [Verified from source: notes/delivery-and-tests.md §3.2; repository-inventory.md]

## Boundary summary

Port the harness engine behind a `DeerFlowClient`-shaped facade (A1–A19 plus the C-items' kept essence); treat everything the gateway/frontend/channels add as replaceable transport (B), with exactly seven seam behaviors (C1–C7) deliberately carried across the line. The parity spec already exists as tests: ~55% of `backend/tests/` is engine-behavior, with the middleware chain-order pin and the §6 deep-read files in `notes/delivery-and-tests.md` as the acceptance core. [Verified from source: notes/delivery-and-tests.md §5–§7]
